# Frozen-Upstream Passage-Plus-Spans Replay Design

**Date:** 2026-08-08

**Status:** Approved intervention boundary; implementation awaits written-spec
review.

**Scope:** A fixed-trace causal diagnostic over the committed Qwen3-1.7B Gate C
artifacts. This design changes no production pipeline, retrieval policy, frozen
manifest, or SPEC contract.

## Goal

Measure whether giving QA the recorded retrieved passages in addition to the
recorded normalized Extractor spans closes the observed multi-agent accuracy
gap. The experiment must isolate QA-visible context from retrieval and routing:
Planner output, Step Definer routes and tasks, retrieval titles, source passages,
Extractor outputs, executed-step topology, and the original stop reason remain
frozen. QA and the strictly downstream `plan_summary` are regenerated.

The experiment reports both:

1. a QA-level mechanism endpoint, before summarization; and
2. the normal scored final answer after a regenerated plan summary, compared
   with the untouched recorded `single_fp16` arm.

Despite its historical name, the recorded `single_fp16` arm is Qwen3-1.7B
**4-bit**, not FP16. It is never regenerated by this experiment.

## Motivation

On the 128 questions where the multi-agent run retrieved both gold passages,
its final F1 is 0.3141 against the single-hop arm's 0.5133. Literal gold-answer
survival falls from 84/128 raw Extractor outputs to 52/128 normalized QA inputs:
42 questions are already missing the answer in raw Extractor output and 34 lose
it during normalization. The exact matcher therefore causes substantial loss,
but permissive lexical matching also admits many irrelevant or entity-substituted
sentences. Re-running QA with the complete passages is the direct contract test;
further retrieval work is out of scope.

## Approaches Considered

### Selected: fixed recorded trace, regenerated QA and summary

Replay every recorded QA call from immutable artifact state, add recorded
passages only to question-answering calls, propagate regenerated QA state into
the one downstream aggregate call and all plan summaries, and compare with both
the old MA answers and the untouched single-hop answers. This is the smallest
design that isolates passage access while producing a final-answer metric.

### Rejected: live downstream pipeline rerun

Allowing new QA answers to alter Step Definer tasks, follow-up queries, retrieval
titles, or the executed-step graph would measure a compound architecture change.
It is also impossible for source traces that stopped early because their
counterfactual later tasks and passages were never recorded. The current branch
uses a different retrieval policy from source commit `56cd63f`, so invoking the
current orchestration would additionally introduce version drift.

### Rejected: QA-only or frozen-summary replay

Pairing new QA answers with an old summary built from old answers is incoherent
and discards the intervention before the scored output. A QA-only score is useful
mechanism telemetry but cannot be compared with the source Gate C number because
the plan summary is normally the scored answer.

### Rejected: fuzzy-normalizer treatment

Threshold matching changes which evidence is attributed to which source
sentence and has poor selectivity in this artifact. It answers a different
question from whether full passage access removes the extraction bottleneck.

## Intervention Boundary

| Component | Replay behavior |
|---|---|
| Questions, gold answers, strata | Frozen; used for scoring, never prompt assembly |
| Planner output and full plan | Frozen from the baseline records |
| Step Definer call graph, routes, and task text | Frozen, including every follow-up |
| Retrieval events, queries, titles, rank, and passage sentences | Frozen from the QA and Extractor records; no retriever is constructed |
| Raw and normalized Extractor spans | Frozen; Extractor is not regenerated |
| Executed QA call keys | Frozen at 427 calls |
| QA outputs | Regenerated for all recorded calls |
| Executed-step topology and stop reason | Frozen at the source trace |
| Plan-summary inputs | Rebuilt from the frozen plan/trace plus treated QA state |
| Plan-summary outputs | Regenerated for all 200 questions |
| Single-hop arm | Read-only recorded comparator; no model calls |

The source trace contains 427 QA calls by stage: 200, 187, 32, 7, and 1.
Exactly 426 are question-answering routes, each joined to ten Extractor records,
for 4,260 frozen passage exposures. One step-3 call is an aggregate route. There
are 200 summary calls. The minimum treatment therefore costs 627 scored
generations, not 411; 411 covers only the both-gold subset.

Every source call is identified by `(question_id, stage, call_index)`. Calls are
assembled directly from recorded fields. The harness must not call
`pipeline.build_stage_calls`, because that function derives activity, routing,
grounding, and retrieval from live state.

## Exact QA Treatment

For every question-answering call, reconstruct the original QA fields from its
recorded task and `consumer_input.evidence_blocks[].prompt_spans`. Require the
resulting canonical message-object hash to equal the source
`rendered_prompt_sha256`. Then replace only the `{evidence}` field with:

```text
<the original spans-only evidence, byte for byte>

Retrieved passages for the current step:
[1] <recorded title>: <recorded sentences in source order>
...
[10] <recorded title>: <recorded sentences in source order>
```

The passage block is produced by the repository's existing
`prompts.format_paragraphs`. Titles, sentences, and ranks come from the ten
matching Extractor `consumer_input` records and must exactly match the recorded
QA retrieval-title order. Existing selected spans remain in their original
position and may therefore also occur in the appended passage. This deliberate
duplication makes the intervention strictly additive: no existing evidence is
deleted or reordered. Repeated exposure of selected sentences is a predeclared
property of this treatment, not an accidental deduplication choice. The QA
system and user templates remain unchanged.

The one aggregate route receives no passage. Its frozen route and task remain
unchanged, but its evidence is rebuilt from regenerated, evidence-grounded prior
QA answers because those answers are downstream of the intervention. Freezing
the old aggregate evidence would reintroduce stale QA state. This aggregate is
outside the both-gold subset.

## Treated State and Plan Summary

Parse and salvage regenerated QA output with the existing code. Recompute each
QA answer's grounding against the evidence actually visible in its new prompt:
the normalized spans plus all appended passage sentences, or treated grounded
prior answers for the aggregate route. New grounding can affect aggregate input
and summary labels, but it must never alter the frozen later Step Definer task,
query, retrieval titles, or executed-step set.

Build each summary history from scratch. Preserve the original question, full
plan, ordered step goals/tasks, executed steps, and source `stop_reason`; replace
only QA-derived answer, success, rating, payload provenance, and grounding with
treated values. Regenerate exactly 200 `plan_summary` calls with the unchanged
summary prompt. Resolve the scored answer with the existing precedence:
`summary_parsed`, `summary_salvaged`, reverse usable QA fallback, then empty.

Regenerated `success` can disagree with the frozen trace. The primary estimand
intentionally conditions on the recorded call graph: it can continue after a
new `success=no`, and an originally stopped trace cannot grow after a new
`success=yes`. Report all success-field disagreements. As a sensitivity result,
compute the QA-level prediction after truncating treated history at the earliest
new `success=no`. Original-stop/new-success cases are right-censored and cannot
be expanded without violating the frozen-upstream design.

## Model and Execution Contract

Use one `Qwen/Qwen3-1.7B` load for QA and plan summary with:

- resolved model commit
  `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`;
- 4-bit bitsandbytes NF4, double quantization, FP16 compute;
- the source quantization census: 1,720,574,976 nominal parameters,
  1,409,286,144 4-bit parameters, zero 8-bit parameters, and fraction
  0.8190786008502311;
- greedy generation, QA ceiling 96 and summary ceiling 128;
- batch size exactly 4 and the original scored-batch membership/order;
- `models.render_chat` as the only renderer, with `enable_thinking=False`;
- immediate failure if any raw output contains `<think>` or `</think>`; and
- a Tesla T4 (compute capability 7.5) with exact source package versions:
  PyTorch 2.10.0+cu128, Transformers 5.14.1, bitsandbytes 0.50.0, and CUDA
  12.8. A mismatch aborts before generation.

Stage-preserving execution requires 108 QA batches and 50 summary batches.
There are no warm-up generations in the scored treatment.

The source artifact records `resolved_tokenizer_revision=TBD`. The replay loads
the tokenizer from the pinned model commit, hashes its chat template and
tokenizer files, and hashes the exact `models.render_chat` output for every call.
This is stronger forward provenance but cannot retroactively prove the source
tokenizer snapshot. Before the treatment, run a 21-generation reproducibility
sentinel: the first recorded scored batch from each of the five QA stages plus
the first summary batch, using byte-identical source messages and source batch
membership. Raw output, parsed/salvaged payload, and token count must match the
source exactly. Any mismatch aborts the treatment and requires either restoring
the source service identity or approving a full contemporaneous spans-only MA
control.

## Integrity and Failure Handling

The CPU audit phase fails closed unless all of the following hold:

1. all four artifact hashes and internal JSONL hashes match;
2. baseline and single arms contain the same ordered 200 question IDs, questions,
   gold answers, model identity, precision, and experiment fingerprint;
3. the source contains exactly 427 QA calls, 200 summaries, 426 retrieval-backed
   QA routes, one aggregate route, and 4,260 Extractor records;
4. every retrieval-backed QA call joins exactly ten contiguous document ranks,
   and every title equals its recorded retrieval title;
5. every Step Definer task agrees with its QA and Extractor task text;
6. reconstructing all original QA and summary message objects reproduces 627 of
   627 recorded message hashes;
7. scored batch certificates cover every regenerated call exactly once;
8. no gold answer, gold title, supporting-fact label, or retrieval stratum is
   read while assembling model inputs; and
9. every treated prompt plus its output ceiling fits the recorded context
   window after tokenizer rendering.

Write outputs atomically through `.partial` files. A failed audit, model/precision
check, context check, generation, parse-integrity check, or `<think>` check leaves
no complete result certificate. Never resume across a changed treatment
fingerprint.

## Provenance and Outputs

The replay has its own treatment fingerprint and must never reuse the source
experiment fingerprint. Its canonical payload binds:

- all source artifact hashes, source commit, and source experiment fingerprint;
- full and both-gold ordered cohort hashes;
- the frozen semantic trace: plans, call keys, tasks, routes, retrieval events,
  ordered titles/sentences, normalized spans, and stop reasons;
- treatment schema and exact passage formatter source/hash;
- old and new message-object hashes plus tokenizer-rendered chat hashes;
- QA and summary template hashes and versions;
- summary-history, grounding, stop, and finalizer policies;
- model commit, tokenizer hashes, quantization census, package/GPU identity,
  decoding ceilings, batch membership, and `enable_thinking=false`;
- replay code hash/commit and scorer/bootstrap configuration.

The finalized metadata binds that treatment fingerprint to the completed calls
and answers JSONL hashes. Keeping output hashes outside the treatment-fingerprint
payload avoids a circular hash dependency.

Every generated record retains its source parent call key/hash and both source
and treatment prompt hashes. Outputs live under the ignored
`analysis/passage_plus_spans_replay/` directory:

- `manifest.json`: ordered IDs, frozen subset, call keys, and source lineage;
- `calls.jsonl`: model load, 21 reproducibility-sentinel calls, 627 scored
  treatment calls, and their batch certificates;
- `answers.jsonl`: 200 treated answer records;
- `meta.json`: environment, integrity gates, fingerprints, and finalized hashes;
- `summary.json`: metrics, paired tests, mechanism telemetry, and interpretation.

## Metrics

### QA-level mechanism endpoint

For each question, apply `usable_short_answer` in reverse treated trace order and
score that deterministic pre-summary candidate. Report F1, EM, and paired change
against the same source-MA candidate:

- overall n=200;
- both-gold n=128;
- `hidden_bridge` and `fully_named` strata.

Also report last-executed QA and best-intermediate-QA scores as explicitly
secondary/oracle diagnostics, per-step parse and salvage status, success drift,
grounding, literal gold-answer survival, prompt tokens, and the earliest-new-no
truncation sensitivity. Do not average all intermediate answers against the
final gold as if bridge subquestions were final-answer tasks.

### Final-answer endpoint

Score regenerated summary/fallback answers with the existing HotpotQA EM/F1
helpers. Report treatment versus both source MA and recorded single-hop for:

- overall n=200;
- both-gold n=128;
- both retrieval strata;
- wins/losses/ties and final-answer-source distribution;
- 10,000-draw paired bootstrap intervals with seed 20260807; and
- exact two-sided McNemar tests on EM.

Report the fraction of the original MA-to-single F1 gap recovered. Show the
SPEC §15.5 thresholds beside the overall and stratum estimates, but label the
result `Gate-C-comparable fixed-trace diagnostic`, never `PASS_GATE_C` or `GO`.
The treatment violates the current §4.3 QA-input contract and was designed after
observing Gate C; an official acceptance claim requires an approved SPEC change
and a fresh full pipeline run.

## Implementation Surface and Verification

After this design is reviewed, the implementation plan should add only:

- a `clean_room/` replay CLI that reads the committed artifacts directly,
  performs audit-only or GPU execution, and never initializes retrieval; and
- focused tests for trace reconstruction, passage joins and formatting,
  aggregate treated-state propagation, grounding, summary rebuilding,
  fingerprints, source-hash rejection, no-gold prompt assembly, fixed batch
  membership, and final scoring.

No `src/` behavior, prompt template, SPEC text, config, manifest, retrieval code,
or source evidence artifact is modified. Verification includes the complete
CPU test suite appropriate to the new harness, an audit-only run over all source
records, compilation, a diff-scope audit, and the GPU integrity checks above.

## Interpretation Boundary

This experiment estimates the direct effect of passage visibility conditional
on the recorded plan, tasks, retrieval, extraction, and execution trace. Frozen
later tasks may embody old QA answers, so the design can underestimate a
deployable passage-aware pipeline. Conversely, it cannot estimate extra steps
that a newly successful formerly stopped trace might execute. These limitations
are deliberate consequences of removing retrieval and routing drift.

Only after the QA-level and final-answer results exist should the team decide
whether §4.3's extract-then-answer contract warrants a proposed change.
